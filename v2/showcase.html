A 10-Minute Lecture

Agentic Loops

Why some AI tasks need one prompt, and others need a program that keeps checking its own work until it's actually done.

For anyone who has used an AI chat tool but never built with one. No coding background required to follow along — a few examples use code, but the ideas don't.

The Core Idea

What is an agentic loop?

Ask an AI model a question and it gives you one answer, then stops. That's a single prompt: one input, one output, done. An agent is different — it's a program that can take actions on its own, like editing a file, running a command, or browsing a page, instead of only producing text for a person to act on. An agentic loop is what happens when you let that agent repeat: it acts, checks what happened against some goal, and decides whether to act again or stop. Each pass through that cycle is called an iteration.

The part that makes it a loop and not just "asking the AI a few times" is the check in the middle. A loop needs a stopping condition — a rule, checkable by the program itself, for when the work is actually finished. Without one, a loop doesn't know when to stop, and neither do you.

How it repeats

If the check fails, the loop returns to "Agent acts" — not back to the very start — and keeps retrying with the last attempt in hand, until the check passes or a round limit is reached.

Why the check has to be real

A trustworthy check doesn't grade itself by feel — it's a test suite, a comparison, a rendered screenshot, something that doesn't depend on the same source that might have made the mistake. Asking the model "did this work?" isn't a real check, since it can be wrong about its own answer the same way it was wrong about the task.

When It's Worth It

When to use one

A loop costs more than a single prompt — more time, and more calls to the model. That cost is worth paying only when a few things are true about the task in front of you.

You can check the answer in code

If a program can verify success — tests pass, a value matches, a page renders without errors — the loop can grade its own work instead of waiting on a person.

One attempt usually isn't enough

Loops earn their cost on problems that typically take a few tries, like fixing a bug or matching a design spec — not on things a model usually gets right the first time.

You can define "done"

A loop needs a stopping condition stated concretely enough to check, not a vague sense of "good enough" that only a person could judge.

An extra attempt is cheap

Each iteration costs time and money. Loops make the most sense when a wrong attempt is inexpensive to throw away and try again.

If most of these don't hold — the check would really have to be a person's judgment call, the task usually comes out right on the first try, or a wrong attempt is expensive to undo — a single, carefully written prompt is very often the better tool. A loop is a specific instrument for a specific shape of problem, not a general upgrade over prompting.

The Upside

What loops are good at

The advantage of a loop over a single prompt is not that it's smarter — it's that it doesn't have to be right on the first try, because it checks its own work.

The one that matters most

Catching its own mistakes is the whole point: a single prompt has no way to know it got something wrong, so a mistake just ships. A loop with a real check finds the mistake and tries again before you ever see the bad version.

None of that happens automatically, though. It happens because someone wrote a check worth trusting and gave the loop enough attempts to use it — the loop does the retrying, but a person still does the part that actually requires judgment: deciding what "correct" means in the first place.

What to Watch For

Where loops go wrong

None of this is free, and one of these four problems is more dangerous than the other three combined — precisely because it's the one that doesn't announce itself.

Cost adds up fast

Every iteration is a new model call. A loop that runs eight rounds can cost roughly eight times what a single prompt would.

It can loop forever

Without a hard round cap, a loop with a weak stopping condition can keep retrying without ever converging, burning time and budget.

Worth worrying about most

A broken check is invisible

If the thing verifying success is itself wrong, the loop will confidently converge on a broken answer and report it as done. Everything else in the loop can look healthy while it happens.

It's harder to review afterward

Eight rounds of small edits are harder for a person to audit later than one careful attempt, especially if no one reads the intermediate rounds.

The first two costs are visible — you can watch the round counter climb and the bill grow. The third is not, which is why it belongs at the top of any list of things to check before trusting a loop's output: a loop that reports success can still be wrong, because a passing check only proves the check was satisfied, not that the check was measuring the right thing.

A Loop You Could Actually Run

A worked example

Say a script needs to resize a folder of photos, and a handful of files break the resize because they're corrupted or in an unexpected format. A single prompt saying "write a resize script" produces one script and stops — it has no way to know whether that script actually worked on every file. A loop looks more like this instead.

1
Run the resize script on the whole folder.
2
Check how many files failed, and read the error from the first one.
3
Patch the script to handle that specific failure.
4
Re-run the script on the whole folder again.
Stop when zero files fail, or after six attempts — whichever comes first.

Notice the shape: it's the same four-part cycle from the first section — act, check, decide, repeat — just with the jargon swapped out for a task you could run in a terminal this afternoon. "Checks result" from that diagram is step 2 here. "Agent acts" is steps 1, 3, and 4. A loop only differs from a single prompt at the moment it decides to go around again instead of quitting.

Before You Build One

Three things to decide first

What "done" means, concretely

Write the stopping condition before you write the loop, not after you're three rounds in and still guessing.

How it will check itself

Tests, a rendered screenshot, a diff — something other than the agent's own opinion of its own work.

What the round cap is

Decide the budget, in rounds or in dollars, before you start — not once you're already worried about the bill.

A loop is worth building exactly when a single prompt would have needed you to check the work yourself anyway. The loop just does that checking automatically, and knows to stop the moment it's actually done. That's a genuinely narrow claim, not a hype cycle — most tasks still don't need one, and the failure modes above are real costs, not hypotheticals. But for the tasks that do fit — checkable, iterative, cheap to retry — the difference between a loop and a single prompt is the difference between asking once and asking until it's right.
